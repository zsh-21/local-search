# 代码守护者 (Code Guardian)

此技能强制执行严格的代码修改指南，确保代码质量达到生产环境提交标准，同时尊重用户意图并保持语言一致性。

## 核心规则

1.  **代码零报错原则 (Zero Error Principle)**：
    *   **必须**确保修改后的代码能够通过 TypeScript/Linter 检查。
    *   **严禁**引入未使用的变量、未定义的类名或类型、过时的导入等影响代码提交的问题。
    *   在提交任何修改前，必须自检是否满足“直接提交代码”的要求。

2.  **UI/UX 与主题一致性原则 (UI/UX & Theme Consistency)**：
    *   **必须**确保新增或修改的功能在视觉上与当前项目的主题（深色/浅色模式）完全统一。
    *   **必须**复用现有的 CSS 变量、设计规范和组件样式，严禁引入突兀的样式。
    *   在涉及复杂 UI 交互、布局调整或视觉增强时，**必须**直接配合使用 `ui-ux-pro-max` 技能以确保卓越的用户体验。

3.  **最小改动原则 (Minimal Scope Principle)**：
    *   **严禁**修改与当前任务无直接关联的代码。
    *   即使周围的代码看起来“不优雅”、“过时”或“可以改进”，**除非**用户明确要求重构，否则**绝对不要动**。
    *   严格将修改范围限制在请求的功能点内。

4.  **最新代码与用户上下文优先 (Latest Code & User Context Priority)**：
    *   **必须**以最新的代码状态为修改基准。如果用户手动修改了代码，将其视为“唯一真理 (Source of Truth)”。
    *   **不要**为了匹配旧的上下文或所谓的“更整洁”版本而回退用户的手动更改。
    *   在合并或应用更改时，始终优先保留用户当前的代码状态，确保手动修改与自动生成的部分完美融合。

5.  **强制代码注释 (Mandatory Code Comments)**：
    *   **每一次**生成代码时，必须为关键逻辑、方法、变量增加中文注释，无需用户额外要求。
    *   注释应简洁易懂，准确说明代码意图。

6.  **组件拆分与规范化 (Component Decoupling & Structure)**：
    *   **必须**保持代码的可复用性。能够拆分成独立组件的逻辑应主动拆分到新文件中。
    *   **图标与 SVG 资源**：必须放置在专门的文件夹下（如 `src/assets/icons` 或 `src/components/icons`），不得在业务代码中内联超长 SVG。

7.  **健壮性与可扩展性 (Robustness & Extensibility)**：
    *   编写代码时必须考虑边界情况、错误处理以及未来的扩展性。
    *   遵循 SOLID 原则，确保代码易于维护和测试。

8.  **中文优先原则 (Chinese Language First)**：
    *   所有的**注释**、**文档**、**描述**以及**与用户的对话**，必须使用**中文**。

9.  **手动修改保护原则 (User-Edited Protection)**：
    *   **必须**将用户已手动修改的内容视为“不可回退的基线”，禁止覆盖、回滚或用“更优雅写法”替换其实现。
    *   **严禁**对非相关文件或非相关代码做顺手式调整（包括但不限于：格式化、重命名、抽公共方法、替换写法、移动文件）。
    *   **默认**优先在既有文件与既有结构内完成目标；仅当“无法在现有结构实现”时，才允许新建文件或拆分组件。
    *   **禁止**无明确需求地新增文档类文件（如 README、说明文档等）或为了“补全规范”而引入与任务无关的改动。

10. **组件独立原则 (Component Isolation Principle)**：
    *   当在主文件（如 `App.tsx`）中新增的代码逻辑较为复杂（例如超过 50 行的独立功能块、包含多个 `useEffect` 或状态管理）时，**必须**将其提取为独立的组件文件（如 `src/components/MyComponent.tsx`）。
    *   **禁止**在主文件中内联定义庞大的子组件，以避免文件臃肿和维护困难。
    *   提取组件时，需确保 Props 定义清晰，并正确处理依赖关系。

11. **模块化与可复用原则 (Modularity & Reusability Principle)**：
    *   **每一次**代码生成都必须以“模块化、可复用”为默认目标：优先抽离可复用的组件、Hook、工具函数与类型定义，避免将可复用逻辑写死在单一页面/单一组件内。
    *   **禁止**复制粘贴相同逻辑到多处；当出现重复趋势时，必须通过抽象与复用消除重复（但仍需遵守“最小改动原则”，仅在与当前需求直接相关范围内实施）。
    *   模块边界必须清晰：组件负责 UI，Hook 负责状态/副作用，工具函数负责纯逻辑；跨模块依赖需保持单向、可追踪。

12. **稳定性与回归保护原则 (Stability & Regression Protection Principle)**：
    *   **必须**保证改动不破坏既有行为：需要考虑边界情况、错误路径、空值/异常输入、权限/会员状态差异与性能退化风险。
    *   当改动涉及状态持久化、跨进程通信（IPC）、缓存或全局副作用（事件监听、定时器、动画帧）时，**必须**确保资源正确清理、避免泄漏，并保证“保存/恢复”链路闭环可验证。
    *   任何可能导致白屏/崩溃的改动都必须优先规避：确保 Hook 调用顺序稳定、依赖数组合理、监听器 add/remove 引用一致、异步更新有防抖/竞态保护。

## 使用说明

*   **修改代码时必须始终激活此技能。**
*   在涉及界面变动时，必须检查 `App.css` 中的变量定义，确保支持主题切换。
*   在应用变更后，必须使用 `GetDiagnostics` 等工具验证代码是否存在 Linter 错误。
*   在规划变更时，显式检查并确认没有触碰无关的函数或行。
*   如果发现“最佳实践”与“用户的手动修改”存在冲突，**必须**遵循用户的手动修改。

### 代码示例（必须包含中文注释）

```ts
// 将字符串安全地裁剪到指定长度：空值返回空字符串，超长时追加省略号
export function truncateText(input: string | null | undefined, maxLength: number): string {
  // 兜底：将 null/undefined 统一处理为可用字符串
  const value = input ?? ""

  // 边界：maxLength 非法时直接返回原值，避免抛异常影响原有功能
  if (!Number.isFinite(maxLength) || maxLength <= 0) return value

  // 未超长：直接返回
  if (value.length <= maxLength) return value

  // 超长：截断并追加省略号
  return `${value.slice(0, maxLength)}…`
}
```
